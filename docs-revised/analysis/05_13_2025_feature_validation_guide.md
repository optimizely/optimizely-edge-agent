# Optimizely Edge Agent: v1 to v2 Feature Validation Guide

_Last Updated: Based on detailed analysis from docs-revised/analysis/gemini-04-18-2025/initial-gemini-04-18-25.md_

This document serves as a guide for validating feature parity and expected functionality when comparing Optimizely Edge Agent v1 and v2. It lists core features from v1, their implementation locus, and where corresponding functionality should be found and validated in v2.

| Feature Area                               | v1 Core Functionality & Key Implementation                                                                                                                               | Expected v2 Corresponding Functionality & Key Components for Validation                                                                                                                               | Notes / Initial Parity Assessment (from prior analysis)                                                                                                                                                                                                                                                                                                                                                                                  |
| :----------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Configuration Loading & Validation**     | Loads config with Headers > Query > Body precedence via `_config_/requestConfig.js`. Parses JSON, booleans. Tracks metadata.                                               | Loads config with same precedence via `services/implementations/ConfigurationService.ts`. Typed, explicit validation rules. Tracks metadata and validation results.                                    | **Improved Parity.** v2 is more robust. A detailed key-by-key check for *all* v1 config options against v2's `OptimizelyConfigOptions` and parsing logic is still advisable (covered by T10, T11 in remediation plan). Explicit handling for `X-Optimizely-Enable-FEX` was added (T9).                                                                                                                                       |
| **Request Routing & Mode Determination**   | `index.js` and `coreLogic.js` determine GET (Edge Mode) vs. POST (Agent Mode/API) based on `httpMethod` and path. `X-Optimizely-Enable-FEX` and `sdkKey` control activation. | Entry points (`index.ts`, `vercel.ts`, etc.) -> Composition Roots -> `services/implementations/RequestHandler.ts`. Routes to Edge Mode, Agent Mode, or API based on method/path.                  | **Architecturally Different, Functionally Similar.** v2 is more structured.                                                                                                                                                                                                                                                                                                                                                                |
| **Edge Mode (GET Request Handling)**       | `coreLogic.js`: Fetches datafile, initializes SDK, makes decisions. **Crucially: Reads `cdnVariationSettings` from decided flag variables** for dynamic routing, content fetching (`cdnResponseURL`), forwarding (`forwardRequestToOrigin`), and caching (`cacheKey`, `cacheTTL`). | `RequestHandler.handleEdgeModeRequest` -> `EdgeModeIntegration.processEdgeModeRequest`. Pipeline: `URLMatcher`, `ContentFetcher`, `CacheManager`, `ContentTransformer`, `RequestForwarder`. | **Previously BLOCKER, Now Addressed (T1).** Original v2 analysis showed `EdgeModeHandler` used mock `cdnVariationSettings`. T1 in the remediation plan aimed to fix this by implementing dynamic routing based on decided flag variables, including all related behaviors (fetching, forwarding, caching). **Validation should confirm T1's success comprehensively.** |
| **Agent Mode (POST Request Handling)**     | `coreLogic.js` (`handlePostOperations`): Initializes SDK, parses config, calls SDK `decide`/`track`, returns JSON. API calls routed via `_api_/apiRouter.js`.                  | `RequestHandler.handleAgentModeRequest`: Uses `ConfigurationService`, `DecisionService` (`decide`/`decideAll`), `EventService` (`trackEvent`). API calls via `services/implementations/ApiRouter.ts`.  | **Mostly Parity.** v2 uses dedicated services. Agent mode was considered functionally close.                                                                                                                                                                                                                                                                                                                                                   |
| **Optimizely SDK Initialization & Usage**  | `_optimizely_/optimizelyProvider.js`: `createInstance`, handles user context. Integrates `UserProfileService.js` if KV UPS enabled.                                          | `services/implementations/DecisionService.ts`: `getOptimizelyClient` (with client caching based on `sdkKey` & datafile revision), `getUserContext` (with user context caching).                    | **Improved Parity/Enhanced.** v2 has client/user context caching. `sdkKey` handling inconsistencies (G6) were addressed. Forced decision logic (G5) was reworked and validated.                                                                                                                                                                                                                                                               |
| **Event Dispatching**                      | `dispatchEventToOptimizely` in CDN adapter.                                                                                                                              | `CloudflareEventService.ts` for Cloudflare. `EventDispatcher.ts` was a placeholder for Vercel/Fastly.                                                                                             | **Cloudflare: Robust. Vercel/Fastly: GAP (G3).** T6 in remediation plan is IN_PROGRESS to implement `EventDispatcher.ts` for Vercel/Fastly. Validation needed post-T6 completion.                                                                                                                                                                                                                                                            |
| **KV Store: Datafile Caching**             | `coreLogic.js` (`retrieveDatafile`) checks `datafileFromKV` config, interacts with `kvStore` via adapter.                                                                  | `services/implementations/DatafileService.ts` checks `datafileFromKV`, uses `IStorageAdapter`. Includes in-memory cache layer.                                                                     | **Parity/Enhanced.** v2 has an additional in-memory layer. Robustness of KV interaction for datafiles addressed by `api-kv-parity-implementation-plan`.                                                                                                                                                                                                                                                                        |
| **KV Store: Flag Key Filtering**           | `coreLogic.js` (`retrieveFlagKeys`) checks `enableFlagsFromKV` config, interacts with `kvStore` via adapter.                                                               | `services/implementations/DatafileService.ts` (uses `IFlagStorageService` or `IStorageAdapter`) checks `enableFlagsFromKV`.                                                                          | **Parity.**                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **KV Store: User Profile Service (UPS)**   | `_optimizely_/userProfileService.js` for KV-based sticky bucketing. Integrated into `optimizelyProvider.js`.                                                               | Originally **Not Implemented** in v2 services.                                                                                                                                                            | **Previously GAP, Now Addressed (T2).** Task T2 in `gemini-gap-issues-remediation` plan aimed to implement `KVUserProfileService.ts` using `IStorageAdapter` and integrate it. **Validation should confirm T2's success for KV-based stickiness.**                                                                                                                                                   |
| **Cookie Management & Stickiness**         | `_helpers_/optimizelyHelper.js` and `coreLogic.js` for reading/writing visitor ID and decision cookies. Stickiness via `validStoredDecisions` passed as `flagsToForce`.        | `utils/CookieUtils.ts` and `services/implementations/CookieService.ts`. Integrated in `RequestHandler.ts`.                                                                                            | **Mostly Parity.** Basic cookie read/write for decisions & visitor ID. T3 in remediation plan added E2E tests for cookie-based stickiness (Status: DONE). Full validation for all scenarios beneficial.                                                                                                                                                                                                                         |
| **API Endpoints (General)**                | `_api_/apiRouter.js` with handlers for datafile, flag keys, SDK fetching, variation changes (KV/Optimizely API interaction).                                                 | `services/implementations/ApiRouter.ts` with more structured endpoints for datafile, flag keys, SDK info, admin, decisions, forced variations, debug.                                             | **Enhanced in v2.** v2 offers more comprehensive API. Some specific v1 API paths might differ or be deprecated; needs mapping if specific v1 admin scripts were used.                                                                                                                                                                                                                                                                    |
| **API: `/api/variations`**               | Unclear if a direct equivalent existed; decision data was part of general decide responses.                                                                                  | Originally returned 501 (Not Implemented).                                                                                                                                                                  | **Previously GAP, Resolution Decided (T7).** Task T7 (IN_PROGRESS) in `gemini-gap-issues-remediation` plan aims to remove this and return 404.                                                                                                                                                                                                                                            |
| **API: `/api/admin/cache/clear`**        | No direct v1 equivalent apparent for a generic cache clear API.                                                                                                              | Placeholder, logged only.                                                                                                                                                                             | **GAP.** Task T8 (BLOCKED) in `gemini-gap-issues-remediation` indicates this is being expanded into a separate plan for robust implementation.                                                                                                                                                                                                                                                |
| **API: Admin Authentication**            | Potentially simpler or different for v1's limited admin APIs.                                                                                                                | Basic `X-Admin-Token` check in v2.                                                                                                                                                                  | **Potential Issue.** Sufficiency review and potential enhancement covered by T12 (PENDING) in `gemini-gap-issues-remediation`.                                                                                                                                                                                                                                                                    |
| **Metrics System**                         | No formalized system.                                                                                                                                                      | `IMetricsAdapter` and `CloudflareMetricsAdapter` (though had recording issues).                                                                                                                     | **Enhancement in v2.** Addressed/Improved by T1 in `gemini-gap-issues-remediation` for Edge Mode. If broader recording issues existed (G10), further specific validation needed.                                                                                                                                                                                                                   |

This guide should provide a solid foundation for a new validation effort. Engineers can use it to systematically go through each feature area, understand its v1 roots, know where to look in v2, and have an initial idea of what to expect based on prior analyses and remediation work.
